`goi pack` builds the app and wraps it in the package its operating system
expects:

| `--os` | Package |
| --- | --- |
| `linux` | `dist/linux-<arch>/<name>-<x86_64\|aarch64>.AppImage` |
| `darwin` | `dist/darwin-<arch>/<name>.app` |
| `windows` | `dist/windows-<arch>/<name>-<arch>-setup.exe` |

The target defaults to the host, so `goi pack` on Linux writes an AppImage, on
macOS a `.app` bundle, on Windows an NSIS installer. `--os` and `--arch` choose
another target:

```sh
goi pack                              # host OS and architecture
goi pack --os windows                 # setup.exe, cross-built where NSIS runs
goi pack --os darwin --arch arm64     # an .app assembled anywhere
goi pack --arch arm64                 # host OS, arm64 binary
```

The plain build [`goi build`](/guide/build/) writes stays in the same `dist`
directory, so the binary can still be run directly.

## Identity and icon

`<name>` and `<id>` come from [`goi.yaml`](/guide/goi-yaml/). Both have to be
plain names (letters, digits, `.`, `_`, `-`): `id`, a reverse-DNS value, names
the desktop entry and icon on Linux, the bundle identifier on macOS, and the
uninstall registry key on Windows.

The icon is one PNG, found in this order:

1. `--icon PATH`
2. `icon:` in `goi.yaml`
3. `assets/icon.png`
4. `assets/images/icon.png`
5. `assets/images/<name>.png`

A 256×256 or larger square icon looks right in app menus; a smaller one packs
with a warning. Each package converts it on the way in: a PNG on Linux, an
`.icns` on macOS and an `.ico` on Windows, all generated by `goi pack` itself.
Names 1 and 2 are resolved against the project root, the rest against the
`assets` directory.

## SDL3

The Go binary is static, so the SDL3 runtime is the one thing a target machine
may lack. When the target matches this machine's operating system and
architecture, `goi pack` copies the library `goi doctor` finds next to the
binary, where the loader looks first.

- `--sdl PATH` bundles a specific library (`libSDL3.so.0`, `libSDL3.0.dylib` or
  `SDL3.dll`) instead.
- `--no-sdl` leaves it out; the target system then has to install SDL3 itself.
- A cross target (another OS or architecture) cannot use this machine's library.
  The command warns and packs without it; pass `--sdl` with the target's
  library to bundle it.

The library is compiled on the machine that ran `goi pack`, so it carries that
system's C library and windowing dependencies. Package on the oldest
distribution you support, which is the usual rule for AppImages and bundled
dylibs alike. GPU drivers always stay with the system.

## The Linux AppImage

The image is an AppDir packed with
[appimagetool](https://github.com/AppImage/appimagetool):

```text
AppRun                            starts usr/bin/<name>
<id>.desktop                      the desktop entry, Exec and Icon point at <name> and <id>
<id>.png                          the icon, also copied as .DirIcon
usr/bin/<name>                    the app
usr/bin/libSDL3.so.0              the SDL3 runtime, when bundled
```

appimagetool is taken from, in order: `--appimagetool`, `GOI_APPIMAGETOOL`,
`PATH`, or a pinned download (`1.9.1`, checksum verified) into the user cache.
The first pack therefore needs network access twice: for the tool, and for the
AppImage runtime appimagetool fetches. Later packs reuse both.

A Linux AppImage is built on Linux: appimagetool is a Linux binary. Another
host says so instead of writing a broken image.

Running it:

```sh
chmod +x myapp-x86_64.AppImage
./myapp-x86_64.AppImage
```

Desktop integration (menu entry, icon) is done by the desktop's AppImage
integration, or by extracting the image and copying the `.desktop` file and
icon into place.

## The macOS app

```text
<name>.app/Contents/MacOS/<name>                    the app
<name>.app/Contents/MacOS/libSDL3.0.dylib           the SDL3 runtime, when bundled
<name>.app/Contents/Resources/<id>.icns             the icon
<name>.app/Contents/Info.plist                      the bundle metadata
```

The bundle is plain files, so it is assembled on any host. On macOS the command
also signs it ad hoc (`codesign --force --sign -`), which is the minimum Apple
silicon needs to launch it. Anywhere else the bundle is unsigned: copy it to a
Mac and sign it there. Gatekeeper still quarantines downloads; distribution
needs a Developer ID signature and notarization, which `goi pack` does not do.

`CFBundleShortVersionString` and `CFBundleVersion` are `1.0` and `1` for now.

## The Windows installer

The installer is generated by [NSIS](https://nsis.sourceforge.io/) and installs
for the current user below `%LOCALAPPDATA%\Programs\<name>`, so it never asks
for administrator rights:

- the executable, the icon and `SDL3.dll` when bundled,
- a Start Menu folder and a desktop shortcut,
- an uninstaller and an entry in Add or Remove Programs.

`makensis` is taken from `--makensis`, `GOI_MAKENSIS` or `PATH`; NSIS runs on
Linux, macOS and Windows, so a Windows installer can be cross-built. There is no
downloaded copy: install it with your package manager (`apt install nsis`,
`brew install nsis`, `winget install NSIS.NSIS`).

`goi pack` converts the icon to an `.ico` for the installer and the shortcuts.
The executable itself still carries Go's default icon, because embedding a
Windows resource needs a `.syso` at build time.

## Flags

```sh
goi pack --os linux --arch amd64
goi pack --os darwin --icon art/logo.png
goi pack --sdl /usr/lib/libSDL3.so.0
goi pack --no-sdl                     # system-provided SDL3
goi pack --appimagetool ~/bin/appimagetool
goi pack --makensis /opt/nsis/makensis
goi pack --keep-appdir                # leave the staging directory for inspection
```

`--os js` is rejected: a browser build is not a desktop package.

## What is not packed

The design files, fonts and other assets are already embedded in the binary by
[`goi build`](/guide/build/), so no package ships the `assets` directory. The
packages are not signed beyond the macOS ad-hoc signature, carry no update
information, and have no version metadata beyond the `.app` plist defaults.
