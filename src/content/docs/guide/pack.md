`goi pack` builds the app and wraps it in the package its operating system
expects:

| `--os` | Package |
| --- | --- |
| `linux` | `dist/linux-<arch>/<name>-<x86_64\|aarch64>.AppImage` |
| `darwin` | `dist/darwin-<arch>/<name>.app` |
| `windows` | `dist/windows-<arch>/<name>-<arch>-setup.exe` |

The target defaults to the host, so `goi pack` on Linux writes an AppImage, on
macOS a `.app` bundle, on Windows an NSIS installer. `--os` and `--arch` choose
another target:

```sh
goi pack                              # host OS and architecture
goi pack --version 1.2.3              # named and stamped package
goi pack --os windows                 # setup.exe, cross-built where NSIS runs
goi pack --os darwin --arch arm64     # an .app assembled anywhere
goi pack --arch arm64                 # host OS, arm64 binary
```

The plain build [`goi build`](/guide/build/) writes stays in the same `dist`
directory, so the binary can still be run directly. SDL3 is the only thing
`goi pack` downloads; the external packagers come from the machine and
[`goi doctor`](/guide/cli/) reports whether they are installed.

## Identity and icon

`<name>` and `<id>` come from [`goi.yaml`](/guide/goi-yaml/). Both have to be
plain names (letters, digits, `.`, `_`, `-`): `id`, a reverse-DNS value, names
the desktop entry and icon on Linux, the bundle identifier on macOS, and the
uninstall registry key on Windows.

[`goi init`](/guide/init/) writes `assets/icon.png` and the `icon:` key, so a
new project packs without any setup. The icon is one PNG, found in this order:

1. `--icon PATH`
2. `icon:` in `goi.yaml`
3. `assets/icon.png`
4. `assets/images/icon.png`
5. `assets/images/<name>.png`

A 256×256 or larger square icon looks right in app menus; a smaller one packs
with a warning. Each package converts it on the way in: a PNG on Linux, an
`.icns` on macOS and an `.ico` on Windows, all generated by `goi pack` itself.
Names 1 and 2 are resolved against the project root, the rest against the
`assets` directory.

## SDL3

The Go binary is static; SDL3 is the one runtime library a package ships, so the
end user never installs it. `goi pack` downloads a pinned SDL3 3.4.20 for the
target once and keeps it in the user cache:

- **Linux** gets Homebrew's build for amd64 or arm64, the only prebuilt Linux
  tarball, since SDL publishes no Linux binary. It targets glibc 2.38 and later
  (Ubuntu 24.04, Fedora 39, Debian 13) and does not inherit the build machine's
  C library.
- **Windows and macOS** get `SDL3.dll` for amd64, arm64 or 386, and the
  universal `libSDL3.0.dylib` for either Mac architecture. The macOS dmg is
  opened with `hdiutil` on a Mac and 7-Zip elsewhere.

The first pack for a target therefore needs network, for SDL3 and for
appimagetool's own runtime download. `--sdl PATH` bundles a specific library
instead, which must be built for the target OS and architecture: `goi pack`
reads its header and rejects the wrong one. `--no-sdl` leaves SDL3 out; the
target system then installs it itself. SDL3 is the only thing `goi pack` downloads: the packagers it runs are
the ones installed on the machine, and [`goi doctor`](/guide/cli/) reports
them. A package that bundles SDL3 also carries its zlib license notice next to
the library.

GPU drivers always stay with the system.

## Tools

`goi pack` runs external tools for two targets, and both come from the machine.
[`goi doctor`](/guide/cli/) lists them as `ok` or `missing` before a pack is
attempted.

### appimagetool (Linux AppImage)

appimagetool is itself a Linux AppImage, so it only runs on Linux:

```sh
curl -L -o appimagetool \
  https://github.com/AppImage/appimagetool/releases/download/continuous/appimagetool-x86_64.AppImage
chmod +x appimagetool
sudo mv appimagetool /usr/local/bin/     # or ~/.local/bin when it is on PATH
```

Use `appimagetool-aarch64.AppImage` on arm64. If it cannot start because FUSE
is missing, run it with `APPIMAGE_EXTRACT_AND_RUN=1` (or install FUSE), or pass
its path with `--appimagetool`.

On macOS and Windows appimagetool cannot run: build a Linux package on a Linux
machine or in a container, and on Windows in WSL2. The `.app` and the Windows
installer do not need it.

### NSIS (Windows installer)

| Host | Install |
| --- | --- |
| Debian, Ubuntu | `sudo apt install nsis` |
| Fedora | `sudo dnf install mingw32-nsis` |
| openSUSE | `sudo zypper install nsis` |
| Arch | `yay -S nsis` (AUR) |
| macOS | `sudo port install nsis` (MacPorts; no Homebrew formula) |
| Windows | `winget install NSIS.NSIS`, `choco install nsis`, or the [official installer](https://nsis.sourceforge.io/) |

`makensis -VERSION` should answer. If it is not on `PATH`, pass its full path
with `--makensis` (on Windows usually
`C:\Program Files (x86)\NSIS\makensis.exe`). NSIS runs on all three hosts, so
a Windows installer can be cross-built from Linux or a Mac.

### 7-Zip (macOS SDL3 away from a Mac)

Only when a macOS target is packed on another host: `goi pack` reads SDL's dmg
with `hdiutil` on macOS and 7-Zip elsewhere (`7z`, `7zz` or `7za` on `PATH`).
Install it with your package manager, or pass `--sdl` with the dylib.

## The Linux AppImage

The image is an AppDir packed with
[appimagetool](https://github.com/AppImage/appimagetool):

```text
AppRun                            starts usr/bin/<name>
<id>.desktop                      the desktop entry, Exec and Icon point at <name> and <id>
<id>.png                          the icon, also copied as .DirIcon
usr/bin/<name>                    the app
usr/bin/libSDL3.so.0              the SDL3 runtime, when bundled
```

appimagetool is taken from `--appimagetool`, `GOI_APPIMAGETOOL` or `PATH`; see
[Tools](#tools) for installing it. A missing one fails before the build.
appimagetool fetches the AppImage runtime on its first run, so that first pack
also needs network. A Linux AppImage is built on Linux: appimagetool is a Linux
binary, and another host says so instead of writing a broken image.

Running it:

```sh
chmod +x myapp-x86_64.AppImage
./myapp-x86_64.AppImage
```

Desktop integration (menu entry, icon) is done by the desktop's AppImage
integration, or by extracting the image and copying the `.desktop` file and
icon into place.

## The macOS app

```text
<name>.app/Contents/MacOS/<name>                    the app
<name>.app/Contents/MacOS/libSDL3.0.dylib           the SDL3 runtime, when bundled
<name>.app/Contents/Resources/<id>.icns             the icon
<name>.app/Contents/Info.plist                      the bundle metadata
```

### Requirements

- **To build one**: any host with Go. `goi pack --os darwin` cross-compiles the
  binary, assembles the plain bundle and downloads SDL3's universal dylib;
  Xcode is not needed. The project still needs its `name`, `id` and icon from
  [`goi.yaml`](/guide/goi-yaml/).
- **To run one**: a macOS release the Go toolchain still supports (macOS 13
  Ventura or later at the time of writing), on Apple silicon or Intel.
- **To sign one**: `codesign` on macOS, which ships with the system.
- **To distribute one**: an Apple Developer ID certificate and notarization,
  which `goi pack` does not do.

Packed on a Mac, `goi pack` signs the bundle ad hoc
(`codesign --force --sign -`), which Apple silicon requires for a locally built
app. Packed anywhere else, the bundle is unsigned.

### Opening an unsigned app

Gatekeeper blocks an unsigned or downloaded `.app` on first launch. For local
use:

- In Finder, right-click the app and choose **Open**, then **Open** in the
  dialog.
- Or open **System Settings → Privacy & Security**, scroll to **Security** and
  click **Open Anyway**.
- If the bundle came from a download, clear the quarantine flag first:
  ```sh
  xattr -dr com.apple.quarantine MyApp.app
  open MyApp.app
  ```
- A cross-built bundle may have no signature at all; sign it on the Mac:
  ```sh
  codesign --force --deep --sign - MyApp.app
  ```
- A bundle moved through a filesystem that drops Unix modes (a Windows zip, for
  example) may lose the executable bit; restore it:
  ```sh
  chmod +x MyApp.app/Contents/MacOS/<name>
  ```

This only makes the app run on your Mac. Distribution still needs a Developer
ID signature and notarization (`xcrun notarytool`), which `goi pack` does not do.

With `--version`, the bundle carries that version in `CFBundleShortVersionString`
and its numeric part in `CFBundleVersion`. A leading `v` and a suffix such as
`-beta` are dropped from those two fields, so `v1.2.3-beta` becomes `1.2.3`;
the file names and the AppImage keep the version as given. Without `--version`
they are `1.0` and `1`.

## The Windows installer

The installer is generated by [NSIS](https://nsis.sourceforge.io/) and installs
for the current user below `%LOCALAPPDATA%\Programs\<name>`, so it never asks
for administrator rights:

- the executable, the icon and `SDL3.dll` when bundled,
- a Start Menu folder and a desktop shortcut,
- an uninstaller and an entry in Add or Remove Programs.

`makensis` is taken from `--makensis`, `GOI_MAKENSIS` or `PATH`; see
[Tools](#tools) for installing NSIS on your host. A missing one fails before the
build. NSIS runs on Linux, macOS and Windows, so a Windows installer can be
cross-built.

With `--version`, the installer and Add or Remove Programs show it as given,
and the fixed version resource gets its numeric part padded to four numbers:
`v1.2.3` becomes `1.2.3.0`, and a version with no digits becomes `0.0.0.0`.
Without it no version resource is written.

`goi pack` converts the icon to an `.ico` for the installer and the shortcuts.
The executable itself still carries Go's default icon, because embedding a
Windows resource needs a `.syso` at build time.

## Flags

```sh
goi pack --os linux --arch amd64
goi pack --os darwin --icon art/logo.png
goi pack --sdl /usr/lib/libSDL3.so.0
goi pack --no-sdl                     # system-provided SDL3
goi pack --appimagetool ~/bin/appimagetool
goi pack --makensis /opt/nsis/makensis
goi pack --version 1.2.3
goi pack --keep-appdir                # leave the staging directory for inspection
```

`--os js` is rejected: a browser build is not a desktop package.

## What is not packed

The design files, fonts loaded through `LoadFont` and other assets are already
embedded in the binary by [`goi build`](/guide/build/), so no package ships the
`assets` directory. A `fontFamily` that names a font installed on the system is
not embedded: the target machine must have that family, or the app falls back to
Roboto. The packages are not signed beyond the macOS ad-hoc signature and carry
no update information.
